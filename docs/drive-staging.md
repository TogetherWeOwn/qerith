# Drive staging preparation metadata

The credential-free Drive CI job tests a closed-admission metadata contract. It
validates an immutable source SHA, GitHub run ID and attempt, the corresponding
run-scoped prefix, and `admission: closed`. Mismatched fields, missing fields and
fields outside the v1 contract are rejected. These tests use synthetic values and
do not access staging secrets.

The manually dispatched, credential-free preparation workflow checks the GitHub
repository, event, main ref, source SHA and checked-out commit before running the
metadata tests. Its guard is not a deployment authorization boundary; a future
secret-bearing workflow must independently enforce trusted source and environment
protection. The preparation job accesses no staging environment or secrets.

This contract does not deploy a Worker, apply migrations, create fixtures, prove
cleanup or retention, or authorize live qualification. No metadata generated by
this code grants admission to staging. Live deployment and qualification require
separately reviewed controls and evidence, including trusted main-only staging
access, verified bindings, bounded cleanup and real integrated interfaces.

## Zero-idle staging requirement

Staging and preview runtimes must not incur recurring always-on runtime charges
when idle. Before admitting live use, inventory the actual Worker, D1 compute,
Containers, Durable Objects and their alarms, scheduled Workers, Stream inputs,
and any other database compute. A sleeping container alone is not evidence that
the rest of the estate is idle or unbilled. Do not add keep-alives, probes,
alarms or schedules that resurrect or sustain resources outside an authorized
use window. Preserve required health and security checks during active use.

A trusted pipeline must start the required resources and verify readiness for
the tested SHA and environment before qualification. It must bound the use
window and retain evidence of startup, readiness and native stop, scale-to-zero,
cleanup or expiry, including after failures and cancellation. Use existing
platform or pipeline controls, not host timers or a new scheduler. An
unsupported control is a prerequisite, not a successful cleanup result.

A recurring always-on exception requires explicit dated owner authorization
recording the resource and environment, recurring cost and expiry or review
date. This requirement authorizes neither new spend nor weaker security, and it
does not replace exact-SHA qualification.

## Staging fixtures and migration admission

Use synthetic data only. Tag test-owned D1 rows and R2 objects with their
originating run ID. Normal success and failure cleanup, trusted main-only
completion cleanup, and a sweep of older tagged leftovers before the next run's
writes are required, as is the staging-only absolute-deadline admission guard.
A leftover row is a recorded cleanup defect, not an admission gate. The reported
R2 lifecycle rule applies only to `drive-qualification/` and expires objects
after three days; the existing seven-day multipart-abort rule is retained. These
are requirements and a reported provider receipt, not proof that cleanup ran.

The staging publish job runs only on a trusted main dispatch in the `staging`
environment, after source and target validation. Staging migrations use Wrangler's
native `d1_migrations` ledger. Log the
pre-apply Time Travel bookmark and pending lists before and after apply for the
exact SHA; the final list must be empty. An uncertain apply requires restoring the
bookmark or recreating the disposable database from migrations before retry.
Worker rollback is separate from database recovery. The staging lifecycle shares
one Actions concurrency group; it does not fence external writers.

Before live qualification, establish readiness for the deployed SHA, record the
previous Worker version or its absence, and implement bounded fixture cleanup.
The current draft does not establish these controls or authorize live use.
Exact-head Actions and independent Security then QA review remain required.
